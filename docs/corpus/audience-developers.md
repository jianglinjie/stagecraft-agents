# Writing for developers

## Lead with specifics
Developers skim for the concrete detail that answers their question, so put it in the first paragraph. Name the version, the command or the limit instead of describing it. A claim such as "fast" needs a number and the conditions it was measured under.

## Show working examples
Every feature explanation should end in something the reader can copy and run. Keep examples minimal: the smallest input that shows the behaviour, with the expected output next to it. Mark placeholders clearly so nobody pastes a fake key into production.

## Avoid marketing language
Superlatives, exclamation marks and vague benefits cost credibility with a technical audience. Replace "seamless integration" with the three steps the integration takes. If there is a trade-off or a known limitation, state it; readers will find it anyway.

## Link to the reference
An article is an entry point, not the manual. Link each concept to its reference page, changelog entry or specification so the reader can go deeper without searching.
